# Отзывы организаций с Яндекс Карт

Приложение подключает карточку организации по ссылке и показывает её отзывы (по 50 на страницу), средний рейтинг,
число оценок и число отзывов. Официального API у площадки нет — данные собираются парсингом.

**Стек:** Laravel 13 (PHP 8.4), Vue 3 + TypeScript, Sanctum (cookie-сессия SPA), PostgreSQL, Reverb.

## Прототип

| | |
|---|---|
| Адрес | `https://dev-g.store` |
| Логин / пароль | `demo@example.com` / `password` |

Пользователь один и создаётся сидером `DemoUserSeeder`, регистрации нет — как в задании.

## Как поднять локально

### docker-compose (рекомендуется)

```bash
cp .env.example .env
docker compose up -d
docker compose exec app php artisan key:generate
docker compose exec app php artisan migrate --seed
```

Приложение — `http://localhost:8000`. Поднимаются: `app`, `nginx`, `node` (Vite), `postgres`, `worker` (очередь
сбора), `scheduler` (плановый ресинк и проверка источника), `reverb` (прогресс по websocket).

Очередь, кэш и сессии хранятся в PostgreSQL. Отдельный Redis не нужен: троттлинг и так пропускает запрос к площадке
раз в ~1,5 с, так что скорость in-memory хранилища на этом объёме ничего не даёт, а лишний сервис усложняет запуск.

### Без docker

Нужны PHP 8.4, Composer, Node 22, PostgreSQL.

```bash
composer setup                            # зависимости, .env, ключ, миграции, сборка фронтенда
php artisan db:seed
php artisan serve
php artisan queue:work --queue=scraping --timeout=900
php artisan schedule:work                 # необязательно
php artisan reverb:start                  # необязательно: без него интерфейс опрашивает статус
```

Проверки: `composer check` (Pint, PHPStan max, 245 тестов), `npm run test`, `npm run test:e2e` (сквозной сценарий в
браузере на своей SQLite-базе). Внешний HTTP в тестах — только записанные ответы площадки.

## Архитектура

Модульный монолит: `app/Modules/{Identity, Organization, Review, Sync, Scraping, Shared}`, в каждом слои
`Domain / Application / Infrastructure / Interfaces`. Модули общаются только через публичные контракты, границы
проверяются arch-тестами.

**Почему так.** Задание — прототип с одним источником, но контекст — сервис для многих площадок. Микросервисы здесь
несоразмерны, а обычный «толстый» Laravel не даёт отделить парсинг от бизнес-логики. Модульный монолит закрывает
оба требования: парсер спрятан за интерфейсом `ReviewSourceGateway`, контроллеры о нём не знают (требование ТЗ), а
Яндекс подключён записью в `config/scraping.php` — вторая площадка добавляется адаптером без правок очереди,
анти-бана и интерфейса.

## Парсинг и обход защиты

Используются те же внутренние запросы, что делает сама страница карточки:

1. `GET /maps/org/{id}/` → JSON из `<script class="state-view">`: название, адрес, рейтинг, число оценок и число
   отзывов (это разные числа: оценка без текста отзывом не считается);
2. `fetchReviews` без токена → площадка выдаёт `csrfToken` и cookies сессии;
3. `fetchReviews` страницами по 50 до конца выдачи — 14 запросов на организацию с 600 отзывами.

**Подгрузка при прокрутке** не нужна: мы запрашиваем те же данные, что подгружает прокрутка.

**Защита от ботов:**
- запрос подписывается параметром `s` (djb2 с XOR по отсортированной строке запроса) — алгоритм перенесён в PHP и
  зафиксирован тест-векторами, которые принял живой сервер;
- у сессии постоянный профиль браузера (User-Agent и клиентские заголовки не меняются между запросами), cookies
  получены от самой площадки, между запросами — пауза со случайным разбросом;
- капча и бан-страницы распознаются, дальше работает анти-бан (пункт 4).

**Предел выдачи.** Яндекс отдаёт не больше ~600 последних отзывов: 13-я страница отвечает ошибкой. Поэтому «все
отзывы» — это `min(отзывов на площадке, 600)`, и интерфейс честно показывает оба числа: собрано и на площадке.

Почему выбран именно этот способ, а не headless-браузер, — в пункте 2 ниже.

## Постраничная навигация: что грузить и кэшировать

**Решение: база данных и есть кэш результата парсинга.** Сбор в фоне сохраняет отзывы, API отдаёт страницу по 50
штатным `paginate()` по индексу; переключение страниц на фронтенде — без перезагрузки, номер страницы в адресной
строке (работают «назад» и ссылка на страницу).

| Вариант | Почему нет |
|---|---|
| Парсить при каждом открытии страницы | секунды ожидания, лишние обращения к площадке и риск бана |
| Держать все ~600 в Redis и листать в памяти | нет истории изменений, данные пропадают при очистке кэша |
| Кэш HTTP-ответов поверх БД | 50 строк по индексу — миллисекунды; кэш добавил бы только инвалидацию и риск показать устаревшее |

Актуальность обеспечивают плановый ресинк и кнопка «Собрать заново».

## Ответы на дополнительные требования

### 1. Устойчивость к смене разметки

HTTP-статус ненадёжен — Яндекс присылает ошибки с кодом 200. Поэтому **каждый ответ проверяется по схеме**:
обязательные поля, типы, диапазоны (оценка 0 или 1..5, дата в ISO-8601, счётчики неотрицательны). Известные ответы
разбираются явно: токен вместо данных — обновить сессию, ошибка за пределом 600 — конец выдачи, `not-found` —
организации нет. Всё остальное — ошибка `source.drift` с точным местом, например
`data.reviews.3.rating must be 0 (no rating) or within 1..5`.

Пустой список отзывов при ненулевом счётчике — тоже drift, а не «отзывов нет».

**Как об этом узнают:** сырой ответ сохраняется в БД для разбора, в лог пишется `critical`, прогон получает статус
«Ошибка» с понятным текстом в интерфейсе и **не повторяется** (повтор не починит парсер), `GET /api/v1/health`
отвечает 503. Кроме того, раз в час `scraping:canary` читает эталонную карточку — поломка видна раньше, чем её
заметит пользователь.

### 2. Внутренние JSON-запросы против headless-браузера

| | Внутренние запросы (выбрано) | Headless-браузер |
|---|---|---|
| 600 отзывов | 14 запросов, ~25 с с паузами анти-бана | страница + XHR + статика, 30–90 с |
| Ресурсы | единицы МБ на воркер | 200–400 МБ на вкладку |
| Хрупкость | подпись, параметры, структура JSON | вёрстка, селекторы, прокрутка |
| Детект бота | по IP и частоте | плюс отпечаток headless-браузера |
| Тесты | офлайн на записанных ответах | нужен реальный браузер |

Замер на живых карточках: 191 из 191 отзыва за 8 с, 600 из 600 — за 24 с.

**Почему выбран этот способ:** он в разы быстрее и дешевле, лучше проходит антибот и тестируется без сети — для
~50 филиалов по расписанию это решающие свойства. **Риск:** подпись и параметры живут в JS площадки и могут
смениться без предупреждения — тогда сбор остановится до правки кода. Поэтому ставка сделана на то, чтобы поломка
была видна немедленно (пункт 1). Браузерный адаптер можно добавить за тем же интерфейсом, не трогая остальную
систему; в прототип он не вошёл — это второй скрапер со своим контейнером и поддержкой.

### 3. Масштаб и фоновая обработка

Сбор выполняется **только в очереди**: запрос создаёт прогон и сразу отвечает 202, работу делает задача
`SyncOrganizationJob` на отдельной очереди `scraping` — медленная площадка не блокирует остальные задачи.

- **Прогресс** сохраняется после каждой страницы и приходит в браузер через Reverb. Если websocket не работает,
  интерфейс сам переключается на опрос: опрос выключается только после первого реально пришедшего сообщения, а не
  просто потому, что websocket настроен.
- **Повторы:** экспоненциальная задержка со случайным разбросом, для бана — отдельная, более долгая. Временные сбои
  (недоступность, 429, бан) повторяются; смена формата и «организации нет» — сразу провал.
- **Ничего не теряется:** страница сохраняется до запроса следующей, повтор продолжает с места обрыва, а не
  начинает сбор заново.
- **Прогон не зависает:** обработчик `failed()` закрывает его и при таймауте или падении воркера.
- **50 филиалов** обновляются не разом: планировщик каждые 15 минут берёт небольшую партию самых устаревших,
  пропуская тех, где сбор уже идёт, и площадку на паузе. Очередь из 50 задач сразу не ускорила бы сбор: темп всё
  равно ограничен паузами анти-бана.

### 4. Анти-бан на объёме

Все запросы проходят через цепочку защит; состояние хранится в общем кэше приложения с атомарными блокировками,
поэтому ограничения соблюдают все воркеры вместе, а не каждый сам по себе.

- **Троттлинг:** минимальный интервал 1,5 с плюс случайная добавка на пару «хост + маршрут выхода».
- **Бэкофф:** экспоненциальный с разбросом; база задержки после бана — 10 минут против 30 секунд для обычных
  сбоев, на 429 соблюдается `Retry-After`.
- **Ротация прокси и User-Agent:** прокси из `SCRAPING_PROXIES`, самый давно не использованный; профиль браузера
  закрепляется за сессией целиком — менять его посреди сессии подозрительнее, чем не менять.
- **«Нас забанили»:** капча распознаётся по маркерам, маршрут уходит в карантин; после серии банов circuit breaker
  ставит на паузу весь хост — воркеры перестают продлевать бан. Плановый ресинк не ставит задачи площадке на паузе.

Сейчас прокси не подключены: работа идёт с IP сервера, пул включается одной переменной без правок кода.

### 5. Идемпотентность и история изменений

- Отзыв уникален по паре «организация + id отзыва на площадке», страница сохраняется одним `upsert` — повторный
  сбор не создаёт дублей. Одна и та же карточка, подключённая разными пользователями, — одна запись.
- Изменение отзыва определяется по хешу содержимого (оценка, текст, ответ организации): новая версия пишется в
  `review_revisions` **только если хеш изменился** — отсюда «было → стало» по каждому отзыву.
- Рейтинг и счётчики снимаются на каждом сборе в `organization_snapshots`; разницу считает бэкенд, на карточке
  видно «+0,1», «+16 оценок».
- Отзывы, пропавшие с площадки, помечаются удалёнными (не стираются) **только после полного сбора**: после
  частичного «не видели» означает «не собрали».
- Каждый прогон хранит статистику: сколько отзывов новых, изменённых, без изменений и удалённых.

## Что доделал бы

- **Публичный стенд со скриншотами** — деплой описан, но адреса пока нет.
- **Браузерный адаптер** как страховка на случай смены подписи — за тем же интерфейсом.
- **Уведомления** о поломке источника в почту или Telegram (сейчас — лог и `/api/v1/health`).
- **Резидентные прокси** и проверка на объёме: у датацентровых IP капча вероятнее.
